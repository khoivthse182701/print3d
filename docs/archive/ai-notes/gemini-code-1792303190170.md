# Business Scenario & Domain Logic Architect Skill

Use this skill whenever the user asks to design a feature workflow, analyze project requirements, draft use-case specifications, or validate business logic before implementation.

## 1. Mandatory 6-Step Business Analysis Pipeline

Never jump into writing implementation code for a complex feature until these 6 business layers are explicitly defined:

1. **Actors, Roles & Permissions Matrix:**
   - Identify every initiating actor (User, Admin, System Cron/Worker, External Webhook) and exact authorization boundaries.
2. **Domain Invariants (Hard Business Rules):**
   - List conditions that MUST ALWAYS hold true regardless of state (e.g., `AvailableCapacity >= 0`, `EndDate > StartDate`, `WalletBalance >= 0`).
3. **Pre-Conditions & Post-Conditions:**
   - **Pre-Conditions:** Required system state before the use case can execute.
   - **Post-Conditions:** Guaranteed state changes, database persistence, and side effects (events/notifications) upon completion.
4. **End-to-End Execution Flows:**
   - **Happy Path (Main Success Scenario):** Step-by-step deterministic execution sequence.
   - **Alternative Flows:** Valid branching paths (e.g., partial payment, coupon applied, manual override).
   - **Exception & Rollback Matrix:** Every failure mode (concurrency conflict, third-party timeout, validation failure) paired with exact HTTP/error codes and compensating rollback actions.
5. **Entity State Machine (Lifecycle Transitions):**
   - Define valid states and strictly forbid illegal transitions:
     `Draft -> PendingPayment -> Confirmed -> Active -> Completed | Cancelled`
6. **Testable Acceptance Criteria (BDD Gherkin Format):**
   - Write concrete `Given / When / Then` scenarios covering boundary values.

## 2. Output Deliverable Template

Always structure the specification output using this exact layout:

```markdown
### [Feature Name] — Business Specification

#### 1. Domain Invariants & Constraints
- **INV-01:** [Rule description & mathematical/logical condition]
- **INV-02:** [Concurrency / Idempotency requirement]

#### 2. State Transition Table
| Current State | Trigger / Action | Guard Condition | Next State | Side Effects / Domain Events |
| :--- | :--- | :--- | :--- | :--- |
| `Pending` | `ConfirmOrder` | `Payment == Paid && Stock > 0` | `Confirmed` | Emit `OrderConfirmedEvent`, Deduct Stock |

#### 3. Execution Scenarios
- **Happy Path:**
  1. Actor submits request with payload...
  2. System validates...
- **Edge Cases & Exception Matrix:**
  | Scenario | Root Cause | System Behavior & Rollback | Error Code |
  | :--- | :--- | :--- | :--- |
  | Race condition on last item | Two concurrent requests | Optimistic concurrency (`RowVersion`) rejects second transaction | `409 Conflict` |

#### 4. BDD Acceptance Criteria
- **Scenario 01:** [Name]
  - **Given** [Initial context]
  - **When** [Action triggered]
  - **Then** [Expected outcome & state verification]
```
